Linux iptables Configuration from Scratch

Mastering raw packet filtering tables (filter, nat, mangle), built-in chains (INPUT, FORWARD, OUTPUT), and rule anatomy (-A, -s, -d, -p, --dport, -m state, -j ACCEPT/DROP).

Key takeaway: Always write idempotent shell scripts with default drop policies and stateful connection tracking.
02

Allow / Deny Rule Logic & Policy Thinking

Understanding first-match-wins semantics and avoiding Shadow Rules (a broad rule placed earlier makes a specific restrictive rule completely dead code).

Key takeaway: Specific drop/allow rules must ALWAYS precede general catch-all rules in the chain.
03

Security Documentation & Gap Analysis

Evaluating real-world configurations against standards like CIS Linux Benchmarks, PCI-DSS Requirement 1, and NIST SP 800-41 to quantify attack surfaces.

Key takeaway: Flag open sensitive ports (SSH 22, DB 3306), cleartext services (Telnet 23), and unrestricted egress.
04

Network Perimeter Defense Understanding

Designing defense-in-depth: DMZ isolation, anti-spoofing bogon filters (RFC1918 drops on WAN), ICMP ping flood rate limits, and egress filtering to block C2 beaconing.

Key takeaway: Firewalls are the first line of defense; misconfigurations account for over 90% of perimeter breaches.

Top Security Interview Questions & Model Answers

Q1: What is a "Shadowed Rule" in a firewall and why is it dangerous?

Answer: A shadowed rule is a rule that will never be reached or executed because an earlier rule in the sequence matches all or a superset of its network traffic criteria. For example, if rule #2 accepts all TCP port 22 traffic from 0.0.0.0/0, and rule #5 attempts to drop port 22 from a known malicious IP 198.51.100.50, rule #5 is shadowed. Because iptables uses first-match-wins, the attacker's traffic is immediately accepted at rule #2, creating a critical security loophole that administrators mistakenly believe is protected.

Q2: Why must stateful connection tracking (ctstate ESTABLISHED,RELATED) be placed at the very top of the INPUT chain?

Answer: Two reasons: Security & Performance. Placing -A INPUT -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT at the top ensures that return packets for legitimate outbound connections (like DNS queries, software updates, or web requests) are instantly permitted without evaluating every subsequent rule in the chain. It drastically cuts CPU load on the firewall kernel and prevents breaking active connections when default policies are set to DROP.

Q3: What is the risk of having an unrestricted OUTPUT ACCEPT policy on a production server?

Answer: If a web application on the server is compromised (e.g. via Remote Code Execution or SQL Injection), an unrestricted OUTPUT chain allows the attacker's reverse shell to connect back to their Command & Control (C2) server over arbitrary ports (like 4444 or 1337) and allows exfiltration of company data. Enforcing egress filtering ensures only authorized outbound destinations (e.g. DNS 53, NTP 123, specific payment API endpoints) are allowed.

Q4: How does iptables differ from nftables and cloud security groups (AWS/Azure)?

Answer: iptables evaluates rules sequentially (top-to-bottom) where rule order is critical. nftables replaces iptables in modern Linux kernels with better performance, a single unified tool syntax, and atomic rule updates. Cloud Security Groups (like AWS SG), however, are declarative and order-independent: all rules are evaluated simultaneously, there are no explicit DENY rules (implicit default deny), and all allow rules are permissive unions.
